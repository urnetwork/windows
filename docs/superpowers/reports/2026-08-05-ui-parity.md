# Windows UI parity audit against Android

2026-08-05. WP3 deliverable. Read from the code on both sides, not from
filenames. **Nothing in the Windows client has ever rendered**, so every
"PRESENT" below means *the code exists and is coherent when read*, never
"works". Treat the whole matrix as a static-analysis result.

Sources:
- Windows: `app/src/App/` on `beta/custom-server` (~12.4k LOC across App/).
- Android: `claude_sandbox_android/app/app/src/main/java/com/bringyour/network/ui/`
  (~19.1k LOC across the screen packages).
- SDK: `claude_sandbox_dashboard/sdk` `beta/custom-server`,
  `cgo/include/urnetwork_sdk.hpp`. Windows consumes the C ABI + C++ wrapper;
  Android consumes the same Go through gomobile. Rows are mapped by the
  underlying SDK function, not by spelling.

The Windows client is **far more built out than the plan assumed**. The connect
drawer, the location chooser, the four detail sheets (contracts, split rules,
per-app split, DNS editor), the whole sign-in flow including guest mode and
wallet sign-in, Stripe checkout with an embedded-WebView2/hosted fallback, and
the balance/usage machinery are all written to a level that matches or exceeds
the macOS reference. What is missing is concentrated in three places: the
**account/settings long tail**, the **wallet/payout/points surface**, and the
**hero visuals** (the connect grid button and the brand fonts).

A second honesty signal: the localization store carries **916 English keys and
the code uses 248 of them**. The strings for payouts, points, blocked
locations, kill switch, device name, auth codes, multipliers, delete account
and the developer surface are all already shipped in
`app/src/App/Strings/*/Resources.resw` — only the UI that consumes them is
absent. Follow-on agents should not be writing new strings.

## Desktop idioms that should deliberately differ

The app is a tray app: `TrayIcon` (Win32 `Shell_NotifyIcon`, four connect x
provide icon states) opens a window via `AppController::ShowWindow(anchor)`,
which positions near the tray on left-click and centres otherwise. "Parity"
therefore means function and brand, not screen-for-screen translation.

- **Bottom-sheet scaffold → scrolling column.** Android's `ConnectScreen` is a
  `BottomSheetScaffold` whose collapsed peek is computed from a fold marker
  (`ConnectSheetGeometry.kt`) so exactly the location row + connect button
  show. On desktop the window IS the sheet; `ConnectView` is one scrolling
  `MaxWidth=600` column. Correct as-is — do not port the peek geometry.
- **Bottom tab bar → `NavigationView PaneDisplayMode="Top"`.** Correct.
- **Full-screen routes → `ContentDialog` sheets.** Android navigates to
  `Route.BrowseLocations`, `ContractStats`, `SplitRules`, `DnsSettings`;
  Windows opens dialogs from tapped cards. Correct, and the one-dialog-at-a-time
  `sheetOpen_` guard is the right constraint.
- **Snackbars → `InfoBar`.** Correct.
- **"Show icon when connected", notification permissions, battery
  optimisation, provide-on-cellular** are Android-platform settings with no
  desktop meaning. Skip them; do not port `ProvideCellPicker`.
- **Wallet deep-links → browser bridge.** `WalletConnect.cpp` drives
  ur.io/wallet-connect and returns over the `urnetwork://` scheme because
  desktop wallets are browser extensions. Correct and already better suited
  than a mobile deeplink port.
- **Where desktop should go FURTHER than mobile:** provider/exit tables,
  reliability metrics and the payouts ledger are cramped on a phone and are
  the natural desktop advantage (see WP4 and build step 6).

## 2. SDK reachability — what is and is not bridged

**The good news is large: almost nothing is blocked on SDK work.**
`DeviceRemote` (`urnetwork_sdk.hpp:9980-10027`) exposes the *complete*
`open*ViewController` set — `Connect`, `Locations`, `Peer`, `Contract`,
`ContractDetails` (client **and** provider), `BlockAction`, `Devices`,
`Feedback`, `NetworkUser`, `Provide`, `Wallet`, `ReferralCode`,
`AccountPreferences`, `PostQuantumIdentity` — plus the whole `Device` base
(settings, provide, block overrides, DNS, `setRouteLocal`, `uploadLogs`,
`refreshToken`).

Every `Api.*` row above runs **in the app process** against the `NetworkSpace`
the `SdkHost` already owns — no bridge, no service, no RPC. That covers
payouts, points, reliability, leaderboard ranking, blocked locations, auth
codes, referral network, payout wallet, delete account and Seeker
verification. **Those ~20 MISSING rows are pure UI work.**

The **DeviceLocalRpc reliability bridge from the Apple port is available here**
and already lands on `DeviceRemote`: `getExits`, `getDestinationExits`,
`getReliabilityMetrics`, `getReliabilitySettings`, `setReliabilitySettings`,
`resetReliabilityMetrics`, `resetReliabilitySettings`, `migrateExit`,
`probeAllExits`, `simulateNetworkChange`, `sync`, `getRemoteConnected`. WP4 can
build the whole developer view against these with no SDK change.

### The genuine gaps — flagged as real work items

| Capability | Android call | Status on Windows |
| --- | --- | --- |
| Drop an exit (fault injection) | `device.dropExit(clientId)` | **LOCAL-ONLY.** `DeviceLocal::dropExit` exists; `DeviceRemote` has no equivalent. Needs an RPC method in the SDK, or a service-side control path. |
| Stall an exit | `device.stallExit(clientId, stalled)` | **LOCAL-ONLY.** Same. |
| Shuffle exits | `device.shuffleExits()` | **LOCAL-ONLY.** `DeviceRemote` has `sync()` and `migrateExit()` but no `shuffleExits`. |
| Probe suite (`startProbeSuite` / `stopProbeSuite` / `probeSuiteRunning` / `getProbeResults`) | not used by the Android UI today | **LOCAL-ONLY.** `DeviceRemote::probeAllExits()` exists but returns `void` and there is no result getter. Any desktop probe UI can only fire-and-forget until this is bridged. |
| First-load timeline, `memoryUsed`, `setPerformanceDegraded`, `getPinnedAppIds`, `tunnelDns*`, `networkChanged` | diagnostics | **LOCAL-ONLY.** Service-side only. |

Also flagged, though not an SDK gap:

- **`ConnectGrid` point data is fetched and thrown away.** `SdkHost::ReadStats`
  (`SdkHost.cpp:876`) calls `connectVc_->getGrid()` and keeps only
  `getWindowCurrentSize()`. `addGridListener` is already subscribed
  (`SdkHost.cpp:839`). Exposing `getProviderGridPointList()` through `LiveStats`
  is a ~30-line change and unlocks the hero visual.
- **`getFilteredLocationState()` is plumbed but discarded.** The
  `LocationsHandler` signature already carries `std::string state`;
  `MainWindow::WireDrawerFeeds` ignores the parameter, so the chooser has no
  loading or error state (`FetchLocationsError` parity).
- **`LiveStats.connectionStatus` is populated and never read.** The connect
  status label is driven only by the *service tunnel* state.

## 3. The connect screen — critical path, in depth

This is the app's reason to exist, so it gets its own assessment. Files:
`MainWindow.xaml:224-516`, `MainWindow.xaml.cpp:996-1003, 1493-1591,
1593-2141`, `LocationSheets.cpp`, `SdkHost.cpp:820-920`.

### What is genuinely there and reads correctly

- A full `ConnectViewController` lifecycle, opened only while the window is
  presented (`SetPresentationActive`), with the device and tunnel surviving in
  the tray. This is the right desktop shape and matches Apple.
- Listener-push stats (`addConnectionStatusListener`, `addGridListener`,
  `addSelectedLocationListener`, `addTunnelChangeListener`,
  provide/peer/contract listeners) marshalled to the UI thread through a
  captured `DispatcherQueue` with `get_weak()` — the threading discipline is
  correct throughout, no strong captures, no UI touches off-thread.
- The location chooser is complete: SDK-bucketed sections (peers, top matches /
  best-available, countries, regions, cities, devices), live search delegated
  to `LocationsViewController.filterLocations`, selection checks, unstable and
  strong-privacy glyphs, brand colour dots from `getColorHex`. It even fixes two
  Android omissions (peer-row and best-available selection checks) and is
  commented as doing so.
- Provide control mode, connection mode, fixed IP, strong anonymisation, post
  quantum, ad/tracker blocker: all wired with an `updatingControls_` re-entrancy
  guard and a read-modify-write of the whole performance profile.
- Peer count with a correct "discovery disabled" state when the RPC is down —
  a nil-tolerance detail Android does not have.
- Insufficient-balance `InfoBar` with an upgrade action that routes guests to
  account creation first.

### What is needed to make it exercisable — precise list

Ordered by how much each blocks "the owner can drive it".

1. **`OnConnectToggle` ignores the selected provider.** `MainWindow.xaml.cpp:998`
   calls `Sdk().ConnectBestAvailable()` in every case. Android connects to
   `connectViewModel.selectedLocation`. Effect: choose Japan in the chooser,
   press Connect, and you silently get best-available. The chooser's own rows
   call `Connect(location)` directly, so choosing a row *does* connect — but the
   main button contradicts it. Fix: read `Sdk().SelectedLocation()` and call
   `Connect(*loc)` when it is set and not `best_available`, else
   `ConnectBestAvailable()`. ~10 lines. **This is the single highest-value fix
   on the critical path.**
2. **No CONNECTING state.** `StatusText` is driven exclusively by
   `OnTunnelStateChanged` (`.cpp:1493`), i.e. by the *service*, and reads
   "Connected"/"Disconnected" only. `LiveStats.connectionStatus` already carries
   `CONNECTED / CONNECTING / DESTINATION_SET / DISCONNECTED` and is dropped on
   the floor. Android maps DESTINATION_SET and CONNECTING to one "Connecting"
   state with an animated ellipsis and a yellow dot. Effect: press Connect and
   the UI says nothing until the tunnel comes up — on a client that has never
   run, that is indistinguishable from a hang. Fix: drive `StatusText` and a new
   status dot from `stats.connectionStatus`, keep the tunnel state as a separate
   signal. The string `connecting_status_indicator` already exists and is unused.
3. **No status dot.** Android colours a dot green/yellow/blue by state. Windows
   has `PeerDot` and `ProvideModeDot` but no connect-status dot. Add one beside
   `StatusText`.
4. **No "ready to connect" idle copy.** Android's disconnected state shows
   `network_name_ready_to_connect {name}` (or the guest variant), which is how
   the user learns which network they are on. Windows shows the bare word
   "Disconnected".
5. **No provider grid.** Android's `ConnectButton` renders a live grid of
   provider points with state colours and success animation — it is the app's
   signature visual and the only place the user *sees* the network working.
   Windows has a rectangular button. Data is already in hand (`ConnectGrid`,
   listener already subscribed); it needs `LiveStats` to carry
   `getProviderGridPointList()` and a `Canvas`/composition renderer of the same
   class as `TransferChart.cpp`. Sizeable but self-contained.
6. **No error surface for connect failures or location fetch failures.**
   `FetchLocationsError` has no counterpart, and `SetLocationFilter`/`EnsureLocations`
   failures are silent. Per the plan's own rule — a mechanism with no observable
   signal does not exist — the connect path needs a visible failure channel
   before the owner tries it.
7. **No reconnect-tunnel affordance.** Android shows a "Reconnect" button when
   the VPN service died under a live connection. The desktop equivalent is the
   service being down; `TunnelStatus` already arrives over the pipe. Coordinate
   with WP2 on the signal, then surface it.
8. **`ConnectButton` never disables during the transition.** Android gates on
   `connectStatus == DISCONNECTED`; Windows lets you spam the button. Trivial
   once (2) lands.

Items 1-4 and 8 together are roughly a half-day of work and turn the connect
screen from "cannot tell what it is doing" into something the owner can drive
and report on. Item 5 is the brand payload and should be its own agent.

   the plan value and the upgrade affordance when `balance_.isPro`.
2. **`SheetBlack` (= `Black.lighten(0.03)` ≈ `#191919`) is absent.** Android
   lifts sheets off the background. Windows `ContentDialog`s use
   `colors::BackgroundBrush()` = `#101010` — the same value as the page behind
   them, so every sheet loses its edge against the app. Add `kSheet` and use it
   in `MakeDialog` (`LocationSheets.cpp:110`) and the equivalents in
   `StatsSheets.cpp` / `BalanceSheets.cpp` / `AuthSheets.cpp`.
3. **`OffWhite` `#F8F8F8` is absent.** Android's `onBackground`/`onPrimary` is
   off-white, not pure white; Windows uses `#FFFFFF` for all body text. Minor,
   but it is a real 1-value divergence in the most-used colour in the app.
4. **The brand fonts are entirely absent.** Android ships ABC Gravity
   (extended + extra-condensed) for headlines, PP Neue Montreal for body, and
   PP Neue Bit Bold for top-bar titles. The Windows repo contains **no font
   assets at all** (`app/src/App/Assets/` holds only `app.ico`, the eight tray
   icons and `ReferralFrog.png`), and every `TextBlock` inherits Segoe UI.
   `BrandText` — the wordmark at the top of the window — renders in Segoe UI
   Semibold. **This is the largest brand mismatch in the client and it is
   invisible in code review because nothing has rendered.** It needs the font
   files added to the project (licensing check first: these are commercial
   faces), registered as `ms-appx:///Assets/Fonts/...#Family Name`, and applied
   as a `FontFamily` resource in `App.xaml` for headings and body.
5. **Ramps are collapsed to single values.** Android carries nine steps of each
   hue (`Blue100..900` etc.); Windows keeps only the one step each surface
   uses. Fine for now — but the hover/pressed states in `WireCardAffordances`
   invent `#242424`/`#2A2A2A` rather than using a ramp step. Harmless; note it
   so a later designer pass has one place to change.

Desktop being *richer* is fine and already happening (hover/pressed card
states, the peers "discovery disabled" state, a real window for the sheets).
None of that is off-brand.
